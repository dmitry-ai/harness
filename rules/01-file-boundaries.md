# Файлы
## FILE-1
Меняй целевые файлы и необходимые зависимости в пределах поручения; сохраняй авторский текст, образцы и чужие изменения.
Перед записью перечитай текущую версию; при конкурирующей правке согласуй изменения, не затирай её старой копией.
## FILE-2
До первой правки существующего `draft.md` в ходе сохрани его реальные байты в соседний `draft.prev.md` и архив с ID хода и файла; проверь совпадение.
Снимок не заменяй промежуточной редакцией; новые пользовательские правки сохраняй отдельно.
## FILE-3
Журнал: указанный пользователем каталог, иначе `ꙮ/1 - Анализ/{req,res}`.
`req/N.md` — дословный запрос; `res/N.md` — полный окончательный ответ, совпадающий с чатом; сохрани до публикации и проверь чтением.
Несколько запросов к одному ответу свяжи явно; не выдумывай промежуточные ответы.
Для основного агента завершение любого ответа, включая анализ самих инструкций, проходит через `answer-prepare` по [контракту завершения](../references/turn-completion.md#подготовка-ответа).
Публикуй проверенные байты без последующего редактирования; подготовленная запись и подтверждённая нативным сообщением доставка — разные состояния.
Независимый сверщик сохраняет фактически отправленный текст по [правилам сверки](../references/turn-completion.md#нативная-сверка); конфликт не разрешает перезапись истории.
## FILE-4
Номер резервируй по обеим папкам; не перезаписывай занятую пару.
Состояние и блокировки размещай в `ꘖ/data`, изолируя разные журналы и исходные файлы.
Токен восстановления связывай с точным журналом, номером и хешами; совпадение запросов не доказывает владение.
## FILE-5
Агентские файлы — внутри `ꘖ`; исключения: запрошенный журнал, контекст, корневая папка `source/` с вложениями клиента, первоначальное создание структуры по [INIT-1](09-initial-analysis.md#init-1) и блоки сайта/Red Flags корневого `.md` по [INIT-5](09-initial-analysis.md#init-5).
По поручению подготовить или изменить proposal работай также с пользовательскими файлами `result/**` и снимками `draft.md` по FILE-2, сохраняя существующую структуру и версии.
Различай результат, постоянное доказательство и временный материал; удаляй лишь последний, когда он больше не нужен.
Перед удалением проверь абсолютный путь, владение и перенаправления ссылок; неоднозначный файл сохрани.
Исполняемый код хранится только в общем инструментарии, не создавай одноразовые `.py` в проектах. В Windows PowerShell конвейер `| python` без явной UTF-8 перекодирует кириллицу и `ꘖ`/`ꙮ` в `?`, поэтому не-ASCII входы `candidate/spec/plan/answer` сначала записывай в UTF-8 файл внутри `ꘖ/data/scratch` (`write_file` или `[System.IO.File]::WriteAllText(..., [System.Text.UTF8Encoding]::new($false))`) и передавай с `--consume-input` (либо перед `|` задавай `[Console]::InputEncoding = [Console]::OutputEncoding = $OutputEncoding = [System.Text.UTF8Encoding]::new($false)`). После подтверждённой записи удаляется только неизменившийся вход; ошибка/конфликт сохраняет его.
`incoming` — staging до импорта: после копирования и проверки уникальных материалов в Evidence и квитанции `intake-drain` он опустошается. Возраст не разрешает удалять единственный исходник.
Не используй `git clean`, массовый откат или признак untracked как разрешение удаления.
