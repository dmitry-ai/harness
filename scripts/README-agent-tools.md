# Среда и интерфейс

`/upwork-cleanup` — общий навык очистки пустых автосозданных проектов в Antigravity и Codex C1/C2.
Внутренняя команда `upwork_project.py cleanup --platform codex` (либо `antigravity`) показывает предварительный результат; `--apply` удаляет регистрации и опустевшие ветки Folders.
Критерий: строго больше 72 часов и ноль бесед во всех трёх хранилищах, включая архивные/дочерние, по ID или рабочему каталогу.
Неизвестная история блокирует удаление соответствующего проекта.
Проекты с подтверждёнными беседами исключаются из ошибок происхождения старого `/upwork-init`: они учитываются в `preserved` и `discovery.excluded_with_conversations`, а в пользовательском отчёте — только общим числом сохранённых.
Закрытый необходимый профиль Codex даёт `pending` без отложенной операции; после его открытия команду нужно повторить.
Частичное удаление сохраняет минимальную `cleanupHold` до повторного запуска, который завершает нативную очистку и удаляет привязки из общего каталога.
Весь `proposals/daily` остаётся неизменным; его `ꘖ/data/projects.json` — индекс исторических вакансий.
Для новых `init` точное время создания хранится в `ꘖ/project.json:created_at`; повторный init его не меняет.
Окончательный ответ `/upwork-cleanup` до публикации передаётся через stdin в `cleanup-report --answer - --platform <среда>`.
Команда сохраняет полный текст в `AI/log/cleanup/YYYY/MM/DD--HH-mm.md`, добавляя первую строку `YYYY-MM-DD HH:mm UTC+3` по Europe/Istanbul; в чат возвращается дословное поле `answer`.
Для нескольких ответов в ту же минуту добавляется суффикс `--2`, `--3` и т. д.; прежние логи сохраняются.

Пользователь начинает `/upwork-init <URL>` и продолжает обычным сообщением в том же чате.
Работу по тому же каталогу можно продолжить в новом чате другой системы, включая полуручную подготовку proposal по отдельному поручению.
Команды ниже выполняет агент; Python 3.12+, зависимости в requirements-agent-tools.txt.
Общий вход: `python <scripts>/upwork_project.py <команда> --help`.
Одна общая библиотека обслуживает Antigravity и Codex; корень workspace, daily-каталог, модели, часовой пояс и пути задаёт `../runtime.json` версии 2.
Всем операциям передавай `--platform antigravity|codex`; прежний вызов без параметра сохраняет совместимость Antigravity.
Codex определяет C1/C2 по CODEX_HOME; для явного выбора есть `--codex-profile C1|C2`. Параметр `--profile` у extract по-прежнему выбирает профиль извлечения.
Только при регистрации из среды без CODEX_HOME допускается настроенный platforms.codex.registration_profile; чтение доказательств остаётся привязано к явно известному профилю.
Адаптеры сред находятся в agent_tools/platforms; доменная логика, KB, журнал, этапы и экспорт общие.
`doctor` сообщает хеш версии всех статических инструментов/правил/справочников, существующие пути и параметры запуска.
Неизменный статический doctor можно использовать повторно; выбранная вкладка, модель и фактическая загрузка правил проверяются в текущей сессии отдельно.
`install-global` дополняет нативные манифесты skill/worker, сохраняя остальные entries; общие правила анализа глобально не устанавливает.
`build-native [--root <корень>] [--check]` строит или проверяет нативные представления Codex из общих правил, навыка, worker и runtime. Python не копируется.
Сборка создаёт корневой `AGENTS.md` с коротким загрузчиком канонических правил; тот же загрузчик сохраняется в native `developer_instructions` в `.codex/config.toml` для совместимости, без корневого CODEX.md и без копирования полных политик в роли. Модель/effort основного чата выбираются в UI; сборка их не задаёт.
`AGENTS.md` создаётся при запуске `build-native` до нового чата; новый чат читает готовый файл. `build-native --check` только проверяет его наличие и актуальность, без записи.
Существующие посторонние TOML-секции сохраняются. Управляемые документы защищены хешами в ꘖ/data/native-config.json; неизвестная ручная правка требует разрешения конфликта, без её перезаписи.
Изменение набора путей/ролей/runtime требует build-native, затем build-native --check и нового чата; тексты существующих источников читаются актуальными по своим путям.

Подробный порядок команд, этапов и источников — [workflow.md](../skills/upwork-init/references/workflow.md).
Код возврата upwork_project: 0 — выбранная операция выполнена; 1 — вход/структура/сбой; 2 — проверки или публикация требуют действий.
JSON содержит полный список diagnostics, а не только первую ошибку.
Наличие файла и зелёный валидатор не подтверждают истинность или завершённый анализ.

# Создание и продолжение

`inspect URL --output <новый каталог>/source.json [--tab-id <ID>]` один раз читает точно выбранную вкладку.
Снимок содержит observed_at, coverage, доступную историю и ошибки; history_complete=false нельзя трактовать как полную историю.
Вложения сохраняются рядом с ограничениями имени/хоста/размера и фильтрацией credentials при перенаправлениях.
`init URL --from-json source.json --domain <домен или тема> --date YYYY-MM-DD` не делает браузерных запросов.
Дата — первоначальный запрос Europe/Istanbul; принадлежность сайта не устанавливается именем папки.
`--site-hypothesis site.json` передаёт отдельную гипотезу DOC-2: id, essence, for/against, probability_percent и assessment_basis.
Довод содержит argument/source/quote; отсутствие противных данных документируется counterevidence по контракту ниже.

Init создаёт карточку, ручную и агентскую KB, неизменяемый снимок SHA-256, копии вложений с проверкой хешей и общий native manifest.
Повторная внутренняя операция сохраняет номер, ручные документы и ID; штатное продолжение не вызывает init заново.
Рабочий daily-проект регистрируется в `Upwork / Proposals / YYYY / MM / DD`; проверяются project_id, folder_id и folder_path.
В Codex используется Shared-Projects через UI-помощник: shared_id, общий каталог/назначение и profiles с отдельными штатными ID C1/C2. Прямых записей в catalog.json, старые ui-folders.json или базы Codex нет.
Первое штатное создание может ожидать Trust исходного профиля: complete=false/status=pending сохраняются в ꘖ/data/registrations.json; register повторяется до подтверждения. Другие профили восстанавливаются только после наблюдения настоящей исходной регистрации.
`register <проект>` завершает только регистрацию, сохраняя ID/настройки/разговоры.
`configure <проект>` объединяет подключения и обновляет принадлежащие генератору проекции, сохраняя пользовательские источники и настройки.
Обычные init/register запрашивают обе системы по runtime.registration.targets; --platform обозначает исполняющую среду, --target у register выбирает одну регистрацию для исправления.
complete относится к активной системе, all_registered — к обеим; вторичная ошибка/ожидание сохраняется для повтора и сама по себе не блокирует активную работу.
Общий registration.py проверяет имя/корень/папку/нативные ID, до вызова сохраняет intent и затем попытку/результат; last_success сохраняет прежние подтверждённые ID при новом сбое.
Ручное несовпадающее имя не переименовывается молча: конфликт показывает ожидаемое и фактическое значение.
configure объединяет обязательные AG entries с существующими. Общий workspace-loader требует читать правила текущего проекта и path-подключения rules.json; локальный developer_instructions создаётся только при уже существующем ручном override, сохраняя его текст. Иначе наследуются все родительские инструкции. Остальные TOML-поля сохраняются. Проверенный принадлежащий инструменту CODEX.md выводится из эксплуатации.
Повторные пути правил объединяются; inherits/include_only/exclude пока требуют явного разрешения и дают диагностическую ошибку вместо успешной неполной проекции.
configure --check проверяет подключения обеих сред и актуальность проектной проекции без записи.
Прежний штатный context.json обновляется до выбора draft-or-final с сохранением исходных байтов в config-history; пользовательская конфигурация сохраняется.
`--no-register` нужен для изолированной проверки, не обычного анализа.

`status <проект>` читает агентскую KB, хеши, сохранённые вопросы и этапы.
scope=initial_analysis явно ограничивает смысл стадий; proposal_artifacts перечисляет существующие draft/final/предыдущую версию отдельно.
ꘖ/data/continuation.md сохраняет фактическое текущее поручение, рабочие файлы и следующий шаг для другой системы; его наличие не удостоверяет готовность proposal.
Во время полуручной работы читай точный журнал и указанные пользователем result/**, сохраняй исходный draft штатным snapshot_draft.py и выполняй конкретное поручение.
Новые автоматические стадии proposal не добавляются; смена UI сама по себе не требует inspect/init или повторного сбора.
`resume <проект> --reason <причина> [--request-file <точный текст>]` сверяет прежний снимок, сохраняет продолжение и обновляет Progress.md внутри KB; Context.md не читает.
`adopt-requests <проект> --conversation <UUID>` импортирует точные сообщения этого задания из локальных нативных данных выбранной среды: USER_INPUT Antigravity либо user message Codex. Неподдерживаемый формат диагностируется без реконструкции по summary; история другой среды и подготовленные ответы сохраняются.
`stage` принимает явные --input/--output; изменение их хешей делает зависимые этапы устаревшими.
Незавершённый старый проект не объявляется законченным из-за наличия Analysis.json.

# Исследование и доказательства

Вопрос содержит id/question/impact/done_when/inputs/outputs/requirements; примеры в [question.example.json](../skills/upwork-init/references/question.example.json).
`question-add`, `question-claim`, `question-finish`, `question-handoff`, `question-search` сохраняют одного исполнителя, результаты/пробелы и смену метода после трёх пустых поисков.
Это служебный реестр, а не блокировка встроенного search_web; агент соблюдает его в UI.
Вызовы A.A/A.F используют точные существующие входы, ограниченную область записи и критерий окончания.
Программы сравнивают байты/хеши/pointers, A.A оценивает причины и смысл, A.F извлекает/оценивает данные там, где нужна модель.

`collect <проект> --plan <JSON>` пакетно сохраняет GET-наблюдения и извлечение; при повторной записи в существующий отчёт `ꘖ/KB/Evidence/*.json` объединяет прежние `results` без потери наблюдений.
[collection.example.json](../skills/upwork-init/references/collection.example.json) учебный: example.invalid не настоящий источник.
Профили: html (title/meta/meta_all/canonical/текст/разделы/anchors/links/JSON-LD), shopify (публичный JSON + детерминированная сводка `summary` по коллекциям объектов: `record_count`, `timestamp_ranges`, `field_counts`), tracking (идентификаторы и literal JSON), document (текст/PDF/DOCX с Markdown, для JSON — `summary`).
`extract <проект> <observation> --profile <имя>` повторно извлекает из сохранённого ответа, без нового HTTP-запроса.
`extract-file <проект> <путь внутри проекта> --profile document` сохраняет извлечение вместе с хешем исходника.
`sync-attachments <проект> [--media-descriptions <JSON|->] [--no-fetch-videos]` синхронизирует все вложения клиента в корневую папку `source/` и `ꘖ/KB/Evidence/Attachments/`, извлекает дословный Markdown документов (PDF, DOCX, TXT, MD и др.), расшифровки видео (включая Loom) и расшифровки изображений в обе базы знаний (`KB/Project.md` и `ꘖ/KB/{Project,Projects,Evidence}.md`).
Полные исходники и метаданные остаются в Evidence; модели можно передавать выбранные фрагменты.
Различающиеся URL/headers/scope/context дают разные ключи; значения секретных headers не публикуются в метаданных.
По умолчанию cache 24 часа, ошибки до 5 минут; refresh_reason задаёт причину нового наблюдения.
HTTP 403/404 — завершённое наблюдение недоступности, не повод для слепого повтора.
Ошибка извлечения оставляет ссылку на сохранённый ответ для другого профиля/проверки.
DOM читается отдельной командой capture-dom по точному URL, явно выбранным tab-id и --session-id из runtime text.browser.sessions, после проверки профиля и без навигации; неизвестный HTTP-код остаётся неизвестным.
GET-сборщик не исполняет JS; tracking исходник не доказывает исполнение, JSON товара не равен feed.

# Контракт анализа

Новая публикация требует schema_version 3: first-class facts, тип знания/статус, область, первичные evidence, версионные derived_from и missing_checks.
Точный контракт и ограничения методов — [evidence-contract.md](../skills/upwork-init/references/evidence-contract.md).
Читаемые версии 1/2 используются только для диагностики/восстановления; автоматического повышения до verified нет.
[analysis.example.json](../skills/upwork-init/references/analysis.example.json) и его source/observation — явно синтетические offline fixtures, не факты клиента.

`save-analysis <проект> --candidate <JSON|-> [--expected-sha256 <текущий хеш>]` проверяет структуру и первичное происхождение, сохраняет историю; существующий JSON требует ожидаемый хеш.
`render-analysis <канонический ꘖ/KB/Analysis.json> [--output <Markdown>]` проверяет v3/доказательства и сохраняет прежние публикации; ручные изменения дают сохранённый кандидат и conflict.
`validate-analysis <JSON> --format json --evidence` читает и диагностирует также legacy; --render использует те же требования новой публикации.
Гипотезы в `causes` и `misconceptions` сохраняют альтернативы и различающую проверку; неподтверждённые гипотезы с пустым `against` ограничены `probability_percent <= 75`; в подтверждённых `observation`/`client_report` все самостоятельные числа в `essence` должны подтверждаться первичными цитатами/расчётами; рекомендации — условия и проверку результата; высокое влияние требует оснований.
Расчёт percent_change проверяется Decimal по источникам чисел, одинаковым единицам, явной формуле и округлению; экспертные проценты не являются измерением.

`prepare-experiment <проект> --spec <JSON|->` фиксирует план до наблюдений, включая опровергающие критерии.
`record-experiment <проект> --spec <JSON|->` сохраняет неизменяемый опыт, реальные артефакты, нативные действия, условия и исход; не запускает браузер или код из спецификации.
Assertions читают сырые данные: неверный ожидаемому исход нельзя превратить в verified строкой в отчёте.
Поправка критериев — новая версия плана с --amendment-of/--amendment-reason и новыми измерениями; неудачные/неопределённые опыты сохраняются.
`question-finish` принимает --results <JSON|-> по каждому requirement, в том числе конкретные недоступные проверки; ограниченный результат допустим.

`red_flags` ссылается на identity-тезисы; критерии и статусы — [Red Flags](../skills/upwork-init/references/workflow.md#red-flags).
Рендер ставит риски перед анализом и синхронизирует управляемую секцию первого уровня в конце корневой карточки, сохраняя авторский текст и историю.

# Предметный аудит и KB

Внутренние агенты используют ꘖ/KB и первичные доказательства; Context.md остаётся внешним экспортом.
`prepare-review <проект> --parent <UUID> --spec <JSON|-> --response-file <текст|->` фиксирует текущие запросы, точные байты ответа, карту тезисов, версии KB и Evidence, проверяя подтверждённость всех самостоятельных чисел в `response_excerpt`.
Спецификация risk/basis/request_scope/task_flags/claim_ids/claims не имеет default routine; пример — [review.example.json](../skills/upwork-init/references/review.example.json).
Код пересчитывает минимальный риск по типам новых тезисов; значимые выводы требуют двух независимых A.A, рутинный пересказ — доказанных неизменившихся оснований.
Аудитор получает пакет, исходники и кандидат без желаемого вердикта, однобокого JSON-шаблона и результатов другого аудитора.
В обеих средах он сначала вызывает `review-input` и получает нейтральный `report_contract` со всеми допустимыми исходами; в Codex это также связывает зашифрованное назначение с пакетом.

Исходный JSON-отчёт schema2 охватывает пять этапов, kb_consistency, response и все тезисы карты; оценивает метод, альтернативы, ограничения, способность теста опровергнуть тезис и соответствие сырых результатов зафиксированным критериям (при `outcome: supported` все самостоятельные числа тезиса и `response_excerpt` должны быть подтверждены в `observed` или `tested_claim`).
Независимый аудитор работает строго read-only внутри корня текущего проекта и возвращает этот JSON окончательным нативным сообщением; native-review-proof создаётся после его завершения и проверяет отсутствие `prompt_bias_issues` и `reviewer_isolation_issues`.
`record-review --report <JSON|-> --native-evidence <proof>` сверяет JSON с авторским нативным результатом и сохраняет неизменяемую запись.
Для routine self_review явно укажи review_kind и одинаковые parent/reviewer; это не независимый аудит.
needs_changes/open сохраняются и блокируют завершение; review-disposition записывает родительский разбор отдельно, не заменяя вердикт.
Изменённые существенные выводы, KB, доказательства или ответ требуют нового допуска; повторный неизменившийся сбор не обязателен.
Подробные поля и команды — [workflow.md](../skills/upwork-init/references/workflow.md#независимая-рецензия).

`native-executor-metadata <проект> --conversation <UUID> --role primary|AA|AF [--parent <UUID>] [--save]` читает фактические метаданные выбранной среды, отдельно requested/observed и статус проверки; --save сохраняет неизменяемый снимок.
Codex продолжает сверять модель/effort с фактическим spawn; Antigravity читает доступные generation/executor/model config metadata.
Политика выбора и значения по умолчанию остаются в runtime.json; metadata не запускает модели, неизвестное не подменяется настройками runtime.
Программная квитанция не гарантирует предметную истинность: её проверяет A.A.

# Точный журнал и внешний экспорт

`turn-begin <проект> --platform codex` определяет нативный ход и применимость FILE-3/EXEC-5/DOC-2 независимо от формата текста; Antigravity требует `--conversation <native-uuid> --platform antigravity`.
`answer-prepare <проект> --response-file <точный финальный ответ>` записывает точные нативные запросы и ответ, проверяет read-back и прежние допуски связанных документов/анализа; публикуется именно возвращённый `response_file`.
`journal-sync <проект> --conversation <native-uuid>` независимо сопоставляет завершённый нативный ответ с журналом; пропуск восстанавливается постфактум, расхождение сохраняется конфликтом без перезаписи.
`turn-begin` по умолчанию регистрирует текущую беседу у скрытого локального сверщика; `journal-watch --action status|once|start|stop` управляет только им, а `journal-unwatch <проект> --conversation <native-uuid>` снимает одну регистрацию по явному исключению пользователя.
Точные гарантии и пределы — [в контракте](../references/turn-completion.md#пределы-и-проверка); наличие состояния не доказывает понимание правил, подготовка не доказывает доставку.

`record_step.py --dir <журнал> --req-file request.txt --res-file response.txt [--step N]` пишет точные UTF-8-байты в свободную пару.
`validate_step.py --dir <журнал> --all` проверяет пары и незавершённые резервирования.
`record_step.py --dir <тот же журнал> --recover N --token <токен>` восстанавливает прежнюю запись, не перезаписывая конфликтные файлы.
Служебные записи в ꘖ/data/.journal связаны с каталогом/токеном/хешами; публикация файлов атомарна.
Прежний `record-answer <проект> --response-file <точный финальный ответ>` остаётся низкоуровневой операцией совместимости и восстановления; штатное завершение основной беседы использует `answer-prepare`.
Резервирование всей группы предотвращает потерю номеров после сбоя.
`stage ... finalize` проверяет текущую KB/рецензии/журнал, чистоту `ꘖ/data/scratch`, отсутствие разовых скриптов в проекте и собирает экспорт; это готовность ответа, не подтверждённая доставка в UI.

`generate_context.py --root <проект> --config <проект>/.agents/context.json [--dry-run]` полностью включает объявленные документы и точный журнал, сохраняя авторов и границы.
Секция drafts выбирает в каждом каталоге result непустой final.md, иначе draft.md; обе языковые версии сохраняются, draft.prev.md автоматически не подставляется.
Пустой существующий final блокирует новый экспорт, сохраняя предыдущий Context.md и все исходники.
Групповые запросы отмечаются как относящиеся к одному ответу; все оригинальные пары сохраняются полностью.
Неполные пары/группы, пустой final и отсутствующий обязательный источник блокируют замену прежнего корректного экспорта.
Пути ограничены корнем; экспорт не может заменить источник.
Context.md предназначен для ручной передачи внешнему агенту, прежде всего Gemini DeepThink; внутренние агенты его как KB не используют.

# Остальные инструменты

`snapshot_draft.py <draft.md> --turn <ID>` сохраняет реальные байты в соседний draft.prev.md и архив ꘖ/data/.draft-snapshots; повтор хода сохраняет исходную версию.
`validate_links.py <файлы> --local-anchors` проверяет локальные файлы, anchors и JSON pointers; --unique-urls — явная политика без повторов.
`validate_links.py --readable <файлы>` проверяет LINK-5 в исходном Markdown/тексте/HTML: авторские ссылки содержат пробелы и Unicode; преобразование адреса рендерером не считается ошибкой.
Формируй новые ссылки через `agent_tools.links.markdown_link`; `readable_reference` убирает лишнее кодирование пути/fragment, сохраняя исходные значимые параметры и разделители.
`check-project`, `record-answer`, finalize и общие функции публикации проверяют авторский текст; точные цитаты, код, первичные источники и журнал сохраняют исходные байты.
`validate_anchors.py <файлы> --include-code` проверяет исходный HTML по HTTP; это не доказательство DOM, авторизации или смысла.
Эти standalone link tools: 0 — проверки прошли; 1 — вход/локальная ошибка; 2 — сетевой результат не подтверждён.
`safe_commit.py --repo <корень> --file <путь> -m <текст> [--execute]` сверяет точный индекс, unstaged/conflicts/Markdown, не делает add/push.
`validate_statements.py <каталог>` проверяет непустые .md и Test.md числовых папок; не доказывает истинность.
`metrics <trace.jsonl> ... [--bindings <JSON>] [--project <проект>]` считает новый ввод/cache/output и инструменты по наблюдаемым данным, игнорирует дубликаты шагов, неизвестное не заменяет нулём.

# Жизненный цикл материалов

`incoming` используется только до импорта. `intake-drain` проверяет snapshot/job_id, сохраняет уникальные байты в проектных Evidence, пишет manifest исходный путь → SHA-256/постоянный путь; `--apply` удаляет только проверенные неизменившиеся файлы. Незавершённые/неизвестные captures сохраняются.

`save-analysis --candidate -`, `question-add --spec -`, `collect --plan -`, `record-answer --response-file -` читают UTF-8 из stdin. Файловый вход из проектного `ꘖ/data/scratch` с `--consume-input` удаляется после успешной фиксации при совпадении байтов; к моменту `finalize` каталог `ꘖ/data/scratch` должен быть пуст. Без output collect сохраняет вход. План коллектора целиком хранится в provenance публикации. Не создавай разовые скрипты в проектах (`check-project` отклоняет исполняемые скрипты в `ꘖ/data` и `.agents`).

Каноническая публикация анализа обновляет явный `websites` в корневой карточке: URL/null, role client|target, basis_id identity-тезиса. Управляемый блок защищает ручной текст. Пользовательская KB не меняется. Progress обновляется без архива прежней навигации. Метрики коллектора сохраняют накопительные счётчики и последние 32 диагностических события; старые списки мигрируют без потери известных totals.
