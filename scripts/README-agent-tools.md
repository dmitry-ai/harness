# Среда и интерфейс

Пользователь начинает `/upwork-init <URL>` и продолжает обычным сообщением в том же чате.
Работу по тому же каталогу можно продолжить в новом чате другой системы, включая полуручную подготовку proposal по отдельному поручению.
Команды ниже выполняет агент; Python 3.12+, зависимости в requirements-agent-tools.txt.
Общий вход: `python <scripts>/upwork_project.py <команда> --help`.
Одна общая библиотека обслуживает Antigravity и Codex; корень workspace, daily-каталог, модели, часовой пояс и пути задаёт `../runtime.json` версии 2.
Всем операциям передавай `--platform antigravity|codex`; прежний вызов без параметра сохраняет совместимость Antigravity.
Codex определяет C1/C2 по CODEX_HOME; для явного выбора есть `--codex-profile C1|C2`. Параметр `--profile` у extract по-прежнему выбирает профиль извлечения.
Только при регистрации из среды без CODEX_HOME допускается настроенный platforms.codex.registration_profile; чтение доказательств остаётся привязано к явно известному профилю.
Адаптеры сред находятся в agent_tools/platforms; доменная логика, KB, журнал, этапы и экспорт общие.
`doctor` сообщает хеш версии всех статических инструментов/правил/справочников, существующие пути и параметры запуска.
Неизменный статический doctor можно использовать повторно; выбранная вкладка, модель и фактическая загрузка правил проверяются в текущей сессии отдельно.
`install-global` дополняет нативные манифесты skill/worker, сохраняя остальные entries; общие правила анализа глобально не устанавливает.
`build-native [--root <корень>] [--check]` строит или проверяет нативные представления Codex из общих правил, навыка, worker и runtime. Python не копируется.
Сборка задаёт CODEX.md в project_doc_fallback_filenames и бюджет не менее 65536 байт. Модель/effort основного чата выбираются в UI; сборка их не задаёт.
Существующие посторонние TOML-секции сохраняются. Управляемые документы защищены хешами в ꘖ/data/native-config.json; неизвестная ручная правка требует разрешения конфликта, без её перезаписи.
Новые правила/модели требуют build-native, затем build-native --check и новой сессии с обновлёнными инструкциями.

Подробный порядок команд, этапов и источников — [workflow.md](../skills/upwork-init/references/workflow.md).
Код возврата upwork_project: 0 — выбранная операция выполнена; 1 — вход/структура/сбой; 2 — проверки или публикация требуют действий.
JSON содержит полный список diagnostics, а не только первую ошибку.
Наличие файла и зелёный валидатор не подтверждают истинность или завершённый анализ.

# Создание и продолжение

`inspect URL --output <новый каталог>/source.json [--tab-id <ID>]` один раз читает точно выбранную вкладку.
Снимок содержит observed_at, coverage, доступную историю и ошибки; history_complete=false нельзя трактовать как полную историю.
Вложения сохраняются рядом с ограничениями имени/хоста/размера и фильтрацией credentials при перенаправлениях.
`init URL --from-json source.json --domain <домен или тема> --date YYYY-MM-DD` не делает браузерных запросов.
Дата — первоначальный запрос Europe/Istanbul; принадлежность сайта не устанавливается именем папки.
`--site-hypothesis site.json` передаёт отдельную гипотезу DOC-2: id, essence, for/against, probability_percent и assessment_basis.
Довод содержит argument/source/quote; отсутствие противных данных документируется counterevidence по контракту ниже.

Init создаёт карточку, ручную и агентскую KB, неизменяемый снимок SHA-256, копии вложений с проверкой хешей и общий native manifest.
Повторная внутренняя операция сохраняет номер, ручные документы и ID; штатное продолжение не вызывает init заново.
Рабочий daily-проект регистрируется в `Upwork / Proposals / YYYY / MM / DD`; проверяются project_id, folder_id и folder_path.
В Codex используется Shared-Projects через UI-помощник: shared_id, общий каталог/назначение и profiles с отдельными штатными ID C1/C2. Прямых записей в catalog.json, старые ui-folders.json или базы Codex нет.
Первое штатное создание может ожидать Trust исходного профиля: complete=false/status=pending сохраняются в ꘖ/data/registrations.json; register повторяется до подтверждения. Другие профили восстанавливаются только после наблюдения настоящей исходной регистрации.
`register <проект>` завершает только регистрацию, сохраняя ID/настройки/разговоры.
`configure <проект>` объединяет подключения и обновляет принадлежащие генератору проекции, сохраняя пользовательские источники и настройки.
Обычные init/register запрашивают обе системы по runtime.registration.targets; --platform обозначает исполняющую среду, --target у register выбирает одну регистрацию для исправления.
complete относится к активной системе, all_registered — к обеим; вторичная ошибка/ожидание сохраняется для повтора и сама по себе не блокирует активную работу.
Общий registration.py проверяет имя/корень/папку/нативные ID, до вызова сохраняет intent и затем попытку/результат; last_success сохраняет прежние подтверждённые ID при новом сбое.
Ручное несовпадающее имя не переименовывается молча: конфликт показывает ожидаемое и фактическое значение.
configure объединяет обязательные AG entries с существующими, строит CODEX.md из проектных .agents/rules и дополнительных path-подключений rules.json и обновляет только параметры обнаружения в локальной .codex/config.toml.
Повторные пути правил объединяются; inherits/include_only/exclude пока требуют явного разрешения и дают диагностическую ошибку вместо успешной неполной проекции.
configure --check проверяет подключения обеих сред и актуальность проектной проекции без записи.
Прежний штатный context.json обновляется до выбора draft-or-final с сохранением исходных байтов в config-history; пользовательская конфигурация сохраняется.
`--no-register` нужен для изолированной проверки, не обычного анализа.

`status <проект>` читает агентскую KB, хеши, сохранённые вопросы и этапы.
scope=initial_analysis явно ограничивает смысл стадий; proposal_artifacts перечисляет существующие draft/final/предыдущую версию отдельно.
ꘖ/data/continuation.md сохраняет фактическое текущее поручение, рабочие файлы и следующий шаг для другой системы; его наличие не удостоверяет готовность proposal.
Во время полуручной работы читай точный журнал и указанные пользователем result/**, сохраняй исходный draft штатным snapshot_draft.py и выполняй конкретное поручение.
Новые автоматические стадии proposal не добавляются; смена UI сама по себе не требует inspect/init или повторного сбора.
`resume <проект> --reason <причина> [--request-file <точный текст>]` сверяет прежний снимок, сохраняет продолжение и обновляет Progress.md внутри KB; Context.md не читает.
`adopt-requests <проект> --conversation <UUID>` импортирует точные сообщения этого задания из локальных нативных данных выбранной среды: USER_INPUT Antigravity либо user message Codex. Неподдерживаемый формат диагностируется без реконструкции по summary; история другой среды и подготовленные ответы сохраняются.
`stage` принимает явные --input/--output; изменение их хешей делает зависимые этапы устаревшими.
Незавершённый старый проект не объявляется законченным из-за наличия Analysis.json.

# Исследование и доказательства

Вопрос содержит id/question/impact/done_when/inputs/outputs; примеры в [question.example.json](../skills/upwork-init/references/question.example.json).
`question-add`, `question-claim`, `question-finish`, `question-handoff`, `question-search` сохраняют одного исполнителя, результаты/пробелы и смену метода после трёх пустых поисков.
Это служебный реестр, а не блокировка встроенного search_web; агент соблюдает его в UI.
Вызовы A.A/A.F используют точные существующие входы, ограниченную область записи и критерий окончания.
Программы сравнивают байты/хеши/pointers, A.A оценивает причины и смысл, A.F извлекает/оценивает данные там, где нужна модель.

`collect <проект> --plan <JSON>` пакетно сохраняет GET-наблюдения и извлечение.
[collection.example.json](../skills/upwork-init/references/collection.example.json) учебный: example.invalid не настоящий источник.
Профили: html (title/meta/meta_all/canonical/текст/разделы/anchors/JSON-LD), shopify (публичный JSON), tracking (идентификаторы и literal JSON), document (текст/DOCX).
`extract <проект> <observation> --profile <имя>` повторно извлекает из сохранённого ответа, без нового HTTP-запроса.
`extract-file <проект> <путь внутри проекта> --profile document` сохраняет извлечение вместе с хешем исходника.
Полные исходники и метаданные остаются в Evidence; модели можно передавать выбранные фрагменты.
Различающиеся URL/headers/scope дают разные ключи; значения секретных headers не публикуются в метаданных.
По умолчанию cache 24 часа, ошибки до 5 минут; refresh_reason задаёт причину нового наблюдения.
HTTP 403/404 — завершённое наблюдение недоступности, не повод для слепого повтора.
Ошибка извлечения оставляет ссылку на сохранённый ответ для другого профиля/проверки.
DOM читается отдельной командой capture-dom по точному URL и явно выбранному tab-id, без навигации; неизвестный HTTP-код остаётся неизвестным.
JS не исполняется; tracking исходник не доказывает исполнение, JSON товара не равен feed, текст DOCX не проверяет изображения/верстку.

# Контракт анализа

Проверяемый учебный [analysis.example.json](../skills/upwork-init/references/analysis.example.json) использует [example-source.json](../skills/upwork-init/references/example-source.json).
Для проверки копируй example-source.json в агентскую KB/Evidence изолированного проекта; это синтетические сведения.
Поддерживаются legacy schema_version=1 и версия 2.
Пять обязательных списков: identity, concerns, misconceptions, causes, methods.
Пустой список требует notes.<имя>; отсутствие установленных заблуждений допустимо.
Утверждение: уникальный устойчивый id, essence, for, against, probability_percent (целое 0–100), assessment_basis.
Способ: score_percent и criterion вместо probability_percent; causes.addresses ссылается на concerns, methods.addresses на concerns/causes.
Экспертные оценки не выдаются за измеренные/калиброванные вероятности.

Довод: argument, source и точная quote; вместо source допустим source_id из корневого sources.
Пустое against допускается только с counterevidence: status=not_found/unavailable, непустой reviewed_sources и ограничения limitations.
Недоступная проверка не доказывает отсутствие контрдоказательств.
Документация: documentation=true и проверенный anchor; если подходящего anchor действительно нет — anchor_exception с section и observation сохранённой страницы.
Проверяются раздел и цитата именно в нём, наличие подходящего anchor и целостность сохранённого ответа.
JSON pointer создаёт source-ref; проверяются ~0/~1, индекс массива и цитата конкретного поля.
quote_match=whitespace явно разрешает только нормализацию пробельных символов.
source_sha256 может закреплять конкретную версию источника; адресуемые SHA-256 снимки сверяются автоматически.

`validate-analysis <JSON> --format json --evidence` выдаёт все структурные ошибки и ошибки сохранённых источников; сеть не использует.
`check-project <проект>` добавляет локальные ссылки и структуру агентской KB.
`save-analysis <проект> --candidate <путь> [--expected-sha256 <хеш текущего JSON>]` публикует проверенный кандидат с историей; существующий JSON требует ожидаемый хеш.
`render-analysis <JSON> [--output <Markdown>]` обновляет только известную неизменённую публикацию и сохраняет прежние байты.
Ручная правка/неизвестный файл сохраняются, новая версия уходит в render-candidates с диагностикой конфликта.
Совместимый `validate-analysis ... --render <Markdown>` использует ту же защиту; общего overwrite нет.
`red_flags` задаёт отдельные `RF-CLIENT-INTERMEDIARY` и `RF-WEBSITE-UNIDENTIFIED` с проверяемыми ссылками на identity-тезисы.
Контракт и статусы — [Red Flags](../skills/upwork-init/references/workflow.md#red-flags).
Оба способа рендеринга ставят риски перед анализом и обновляют только управляемый блок в начале `.md` канонического проекта, сохраняя авторский текст и историю.
Отсутствие поля в legacy JSON не снимает прежние предупреждения; явный `[]` означает проверенное отсутствие активных флагов.

# Предметный аудит и KB

Внутренние агенты используют ꘖ/KB и первичные доказательства; новые данные и исправления сразу вносятся в связанные модули.
Progress.md — навигация по стадиям и вопросам в KB; Context.md служит внешнему получателю.
`prepare-review` фиксирует версии входов KB.
Для routine основной A.A выполняет предметную проверку всех пяти этапов и kb_consistency, сохраняет review_kind=self_review и передаёт в record-review одинаковые parent/reviewer; это не независимый аудит.
Независимый нативный A.A используется для спорной оценки и значимых выводов; Antigravity — self/inherit, Codex — дочерний агент с выбором модели родителем.
Значимый спорный вывод/архитектура требует двух независимых A.A по REVIEW-3.
`native-review-proof` читает реальные локальные traces/DB UI только для чтения; `record-review` требует текущий пакет, завершённого независимого исполнителя, обработанные findings и доказательства.
Codex сверяет выбранный профиль, UUID/parent_thread_id/agent_path, реальный spawn_agent родителя, его выбор модели/effort, turn_context и завершение дочернего запуска. При зашифрованном назначении сравниваются исходный и дочерний ciphertext; plaintext из них не восстанавливается.
Аудитор выполняет `review-input <проект> --package <путь> --platform codex` и выводит полный JSON. Проверка требует связанную пару нативного вызова/результата с UUID аудитора, корнем, родителем и хешем текущего пакета. Один вручную написанный JSON-файл этого не заменяет.
Модель/effort Codex выбирает родитель по задаче и доступным моделям. Политика subagents.selection=parent, резерв inherit и значения по умолчанию редактируются в одном runtime.json. Сгенерированные роли не задают model, иначе нативный приоритет роли подавлял бы выбор родителя.
Наблюдаемые модели сверяются при наличии метаданных; точная версия/High могут остаться неизвестными.
Предметный вывод не удостоверяется одним JSON-отчётом или программной квитанцией.
Пакет и квитанции фиксируют также версии первичных Evidence и ручной KB; новый вопрос снимает старую завершённость research и зависимых этапов.
После изменения KB/первичных источников нужны актуальная проверка и рецензия затронутых выводов.

# Точный журнал и внешний экспорт

`record_step.py --dir <журнал> --req-file request.txt --res-file response.txt [--step N]` пишет точные UTF-8-байты в свободную пару.
`validate_step.py --dir <журнал> --all` проверяет пары и незавершённые резервирования.
`record_step.py --dir <тот же журнал> --recover N --token <токен>` восстанавливает прежнюю запись, не перезаписывая конфликтные файлы.
Служебные записи в ꘖ/data/.journal связаны с каталогом/токеном/хешами; публикация файлов атомарна.
`record-answer <проект> --response-file <точный финальный ответ>` связывает несколько ещё не записанных запросов с одним реальным ответом, без вымышленных промежуточных реплик.
Резервирование всей группы предотвращает потерю номеров после сбоя.
`stage ... finalize` проверяет текущую KB/рецензии/журнал и собирает экспорт; это готовность ответа, не подтверждённая доставка в UI.

`generate_context.py --root <проект> --config <проект>/.agents/context.json [--dry-run]` полностью включает объявленные документы и точный журнал, сохраняя авторов и границы.
Секция drafts выбирает в каждом каталоге result непустой final.md, иначе draft.md; обе языковые версии сохраняются, draft.prev.md автоматически не подставляется.
Пустой существующий final блокирует новый экспорт, сохраняя предыдущий Context.md и все исходники.
Групповые запросы отмечаются как относящиеся к одному ответу; все оригинальные пары сохраняются полностью.
Неполные пары/группы, пустой final и отсутствующий обязательный источник блокируют замену прежнего корректного экспорта.
Пути ограничены корнем; экспорт не может заменить источник.
Context.md предназначен для ручной передачи внешнему агенту, прежде всего Gemini DeepThink; внутренние агенты его как KB не используют.

# Остальные инструменты

`snapshot_draft.py <draft.md> --turn <ID>` сохраняет реальные байты в соседний draft.prev.md и архив ꘖ/data/.draft-snapshots; повтор хода сохраняет исходную версию.
`validate_links.py <файлы> --local-anchors` проверяет локальные файлы, anchors и JSON pointers; --unique-urls — явная политика без повторов.
`validate_anchors.py <файлы> --include-code` проверяет исходный HTML по HTTP; это не доказательство DOM, авторизации или смысла.
Эти standalone link tools: 0 — проверки прошли; 1 — вход/локальная ошибка; 2 — сетевой результат не подтверждён.
`safe_commit.py --repo <корень> --file <путь> -m <текст> [--execute]` сверяет точный индекс, unstaged/conflicts/Markdown, не делает add/push.
`validate_statements.py <каталог>` проверяет непустые .md и Test.md числовых папок; не доказывает истинность.
`metrics <trace.jsonl> ... [--bindings <JSON>] [--project <проект>]` считает новый ввод/cache/output и инструменты по наблюдаемым данным, игнорирует дубликаты шагов, неизвестное не заменяет нулём.
Codex использует отдельные token_usage_record.usage, не суммирует накопительные token_count; смешанные выгрузки разных сред требуют отдельных отчётов.
Привязка этапов задаётся явно; без неё unassigned.
--project добавляет зарегистрированные cache hits, новые попытки, поиски/смены метода, пробелы и результаты обработки findings; предыдущая незарегистрированная активность неизвестна.
Токены не пересчитываются в деньги/процент квоты без подтверждённой модели пересчёта.

# Регрессия

`python -m unittest discover -s <.agents>/tests -p test_*.py -v`.
UPWORK_CAPTURE_DIR задаёт чтение сохранённых */source.json; тест создаёт временные проекты и не меняет исходные проекты/браузер.
При очистке удаляй только своё временное; существенные доказательства и текущие резервирования сохраняй.
