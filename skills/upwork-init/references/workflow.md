# Внутренний протокол анализа

Все команды выполняет агент из текущего чата через `scripts/upwork_project.py`; они не запускают LLM.
Добавляй `--platform codex` или `--platform antigravity`; в Codex профиль определяется по CODEX_HOME либо явно через --codex-profile.
`<проект>` — точный существующий корень текущей вакансии, не общая папка code/daily и не другой проект.
Candidate/spec/plan/answer передавай как UTF-8 через stdin (`-`), без промежуточного файла или скрипта в проекте. Если файл нужен для восстановления, используй `ꘖ/data/scratch` и `--consume-input`: успешная проверенная фиксация удаляет неизменившийся вход, ошибка/конфликт сохраняет его. План collect остаётся целиком в provenance публикации.
Все записи доказательств — в `ꘖ/KB/Evidence`, служебное состояние — в `ꘖ/data`; ручная KB сохраняется.

## Продолжение

```text
python <инструмент> status <проект>
python <инструмент> configure <проект>
python <инструмент> configure <проект> --check
python <инструмент> register <проект>
python <инструмент> resume <проект> --reason "quota/power failure/Windows hang"
python <инструмент> adopt-requests <проект> --conversation <UUID текущего родительского чата>
```

`resume` сверяет сохранённый снимок и обновляет навигацию `ꘖ/KB/Progress.md`.
`adopt-requests` через адаптер текущей среды читает точные пользовательские сообщения данного задания, сохраняет нативные ID и не восстанавливает текст по свёрнутому пересказу.
Codex использует read-only native SQLite/session JSONL выбранного профиля; Antigravity — нативные USER_INPUT.
Для нового чата без /upwork-init адаптер требует точного нативного cwd/workspace_uri проекта либо явного «Корень проекта: `<абсолютный путь>`» в пользовательском запросе.
Общий корень репозитория или неоднозначный набор каталогов не подтверждает конкретный проект; явное переключение на другую вакансию закрывает прежнюю область запросов.
Импорт другой среды дополняет прежние точные запросы, сохраняя уже подготовленные ответы.
Если формат базы недоступен, сохрани достоверные точные запросы текущего чата; `resume --request-file <файл>` сохраняет текущий запрос в служебном состоянии.
Не выдумывай старые запросы и промежуточные ответы.
Новая работа использует эти же служебные механизмы после init для сохранения первоначального запроса/снимка, без просьбы пользователю повторить команду.

`status` показывает стадии и хеши KB; завершение не выводится из наличия Analysis.json.
Текущая регистрация обязательна для рабочих daily-проектов; pending или отсутствие квитанции выбранной среды не позволяют завершить identity_init.
При переходе между средами выполни configure/register для существующего корня, без нового init.
Register по умолчанию обеспечивает обе среды; для исправления одной регистрации есть --target.
Новый запрос первичного анализа без записанного ответа снимает завершённость finalize.
`resume` не делает inspect/init, не запускает исполнителей и не читает Context.md.
При старом проекте этапы кроме механически сверенного capture требуют проверки; прочитай уже созданное, не начинай анализ заново.
Если создание самой области было прервано до появления `ꘖ/project.json`, заверши init из известного снимка текущего чата, затем продолжи протокол.

После завершения первичного анализа конкретное поручение по proposal выполняется полуручно по тем же KB, точному журналу, continuation.md и существующим result/draft/final.
Статусы ниже описывают первоначальный анализ; они не объявляют proposal готовым и не требуют нового полного анализа из-за смены системы.
Исходный draft до изменения сохраняется по FILE-2; текущая задача и фактический следующий шаг фиксируются в ꘖ/data/continuation.md.
Запрос только о proposal после завершённого анализа записывай общим `scripts/record_step.py`, не добавляя его как незавершённое поручение первоначального анализа.

## Этапы

`capture → identity_init → research → analysis → review → kb_review → finalize`.
Завершение этапа записывается после проверяемого результата; неизменённые результаты используются повторно.
Входы и выходы — точные пути относительно корня проекта, хеши сверяются при продолжении.
Не объявляй workflow.json, rendered.json или Progress.md доказательством собственного этапа.

```text
python <инструмент> stage <проект> identity_init --input "ꘖ/project.json" --output "ꘖ/data/registration-check.json" --note "Сверены карточки, манифесты и фактическая ветка UI"
```

Сохрани фактическое подтверждение в указанном выходе; не сочиняй результат для квитанции.
`research` требует закрытых вопросов/зафиксированных пробелов; `analysis` — текущих KB/доказательств; дальнейшие этапы — текущей предметной проверки A.A.
В рутинном случае основной A.A сохраняет отчёт `review_kind: self_review` с package/scope/result/findings, а record-review получает одинаковые --parent и --reviewer текущего чата.
Такая самопроверка не является независимой; для significant нужны два независимых A.A.
Если вход/результат поменялся, запись считается устаревшей, а прежние файлы и квитанции сохраняются.
Сбой между публикациями не означает завершения; атомарные записи и текущие хеши позволяют повторить только незавершённую операцию.

## Вопрос и владелец

Спецификация — JSON с `id`, `question`, `impact`, `done_when`, `inputs`, `outputs`.
Входы должны существовать; результаты — точные разрешённые файлы в `ꘖ`.
Пример — [question.example.json](question.example.json); адаптируй фактические пути/вопрос к задаче.

```text
python <инструмент> question-add <проект> --spec -
python <инструмент> question-claim <проект> Q-SITE --owner <наблюдаемый ID исполнителя>
python <инструмент> question-search <проект> Q-SITE --owner <ID> --query "точный запрос" --useful
python <инструмент> question-finish <проект> Q-SITE --owner <ID> --output "ꘖ/KB/Evidence/site-report.json"
```

Владельца проверяют по текущему native UI-прогрессу; строка owner не является ОС-аутентификацией.
После трёх пустых поисков сначала верни пробел или обоснуй `--method-change`; журнал поисков не перехватывает встроенный search_web, агент соблюдает этот порядок.
Пробел закрывается сохранённым отчётом и `--gap "что не проверено и почему"`, не выдуманным подтверждением.
Для остановленного исполнителя используй question-handoff с прежним/новым ID и фактической причиной, проверив UI; не забирай живое задание молча.
Сборщик пишет только разрешённый отчёт; хранилище HTTP-наблюдений управляется инструментом под отдельными блокировками.

## Сохранённые источники

```text
python <инструмент> collect <проект> --plan - --output "ꘖ/KB/Evidence/site-report.json"
python <инструмент> extract <проект> <observation из результата> --profile tracking
python <инструмент> extract-file <проект> "ꘖ/KB/Evidence/Attachments/.../audit.pdf" --profile document
python <инструмент> sync-attachments <проект> --media-descriptions -
python <инструмент> source-ref <проект> "Evidence/данные.json" --part related_descriptions --part "~022..." --part description
```

[collection.example.json](collection.example.json) задаёт requests: URL, профиль (`html`, `shopify`, `tracking`, `document`), scope, при необходимости headers/max_age/refresh_reason.
URL-фрагмент относится к адресу цитаты, а не к отдельному HTTP-запросу.
Различающиеся параметры URL, headers и scope разделяют наблюдения; секретные значения headers в метаданные не записываются.
По умолчанию ответ используется до 24 часов, ошибочное наблюдение — до 5 минут; всегда учитывай observed_at и нужную актуальность.
`refresh_reason` создаёт отдельное измерение; прежнее не заменяется.
Сохранённый HTTP 403/404 — полученный результат; не повторяй его вслепую.
Признак JS/challenge — повод выбрать правильную проверку, не доказательство блокировки реального бота.
HTML/bundle показывает исходник, не исполнение; Shopify JSON не равен реальному Merchant Center feed; текст DOCX/PDF извлекается с гиперссылками и форматированием Markdown.
Все приложенные клиентом файлы сохраняются одновременно в корневой папке `source/` и в `ꘖ/KB/Evidence/Attachments/<sha256>/`, а их полный текст, расшифровки видео (`# Видео:`, `# Ключевые моменты устного комментария (дополнения к тексту документа):`, `# Полная расшифровка аудиозаписи:` с `[MM:SS]`) и расшифровки изображений (дословный текст в `«»`, описание UI, подтверждения и противоречия словам клиента с оценками в `%`) синхронизируются в обе KB (`KB/Project.md` и `ꘖ/KB/{Project,Projects,Evidence}.md`) при `init` и через `sync-attachments`.

Для DOM разрешено только чтение явно выбранной вкладки с точным URL:

```text
python <инструмент> capture-dom <проект> --url <точный URL> --tab-id <явный ID> --cdp-port 9222
```

Инструмент не открывает, не переключает, не обновляет и не закрывает вкладки; несовпадение URL/ID диагностируется.
DOM-наблюдение хранится отдельно и не приписывает неизвестный HTTP-код 200.
Авторизованную проверочную вкладку при необходимости создаёт агент штатным браузерным инструментом в собственной сессии по EXEC-3.

## Анализ и проверка

Канонический контракт проверяет analysis.py; совместимы legacy version 1 и schema_version 2.
Пример структуры — [analysis.example.json](analysis.example.json), данные — [example-source.json](example-source.json); оба учебные, не факты реального клиента.
`for` содержит реальные доводы с источником и цитатой; `against` — доводы либо документированное counterevidence.
Counterevidence: status not_found/unavailable, reviewed_sources, limitations.
Заявление not_found после недоступного источника неверно; укажи unavailable.
Источник можно повторно использовать через sources/source_id; иначе аргумент содержит source.
JSON pointers экранирует source-ref; цитата сверяется именно с указанным фрагментом.
По умолчанию цитата точная; `quote_match: whitespace` явно допускает только канонизацию пробельных символов, не слов/чисел/пунктуации.
Documentation без anchor требует anchor_exception: section + observation; проверяются существование раздела, отсутствие подходящего anchor и цитата в разделе.

```text
python <инструмент> save-analysis <проект> --candidate - --expected-sha256 <текущий хеш из status>
python <инструмент> render-analysis <проект>/ꘖ/KB/Analysis.json
python <инструмент> validate-analysis <проект>/ꘖ/KB/Analysis.json --format json --evidence
python <инструмент> check-project <проект>
```

Для первого отсутствующего JSON expected-sha256 не передаётся; существующий JSON требует ожидаемый хеш.
Сохраняются история JSON и собственных Markdown-версий; чужие изменения дают сохранённый кандидат/конфликт, а не безусловную перезапись.
Неполные рабочие материалы храни в ꘖ/data с явным статусом; они не заменяют завершённый анализ.
Ошибки выдаются одним списком с code/field/claim_id/message/hint; исправляй конкретное и пересмотри зависимые выводы.
Успешная формальная проверка не является доказательством истинности утверждения или завершённого предметного аудита.

## Red Flags

Перед техническим разбором оцени посредничество в текущем заказе и возможность установить целевой сайт.
Основания хранятся в обычных `identity`-тезисах с первичными доказательствами/ограничениями; флаги ссылаются на их ID, не копируют доказательства.
Для новых анализов укажи `red_flags`: список выявленных рисков либо `[]`, если оба проверены и не выявлены.
Отсутствующее поле в старом анализе означает «не оценено», а не отсутствие рисков; старый предупреждающий блок при этом не удаляется.

```json
"red_flags": [
  {
    "id": "RF-CLIENT-INTERMEDIARY",
    "status": "confirmed",
    "summary": "Заказчик ведёт проект конечного клиента через своё агентство.",
    "basis_ids": ["H-IDENTITY-CLIENT"]
  },
  {
    "id": "RF-WEBSITE-UNIDENTIFIED",
    "status": "unresolved",
    "summary": "После проверки вакансии, доступной истории и целевого поиска домен не установлен; нужна ссылка от клиента.",
    "basis_ids": ["H-SITE-1"]
  }
]
```

ID тезисов в примере замени на фактические; для гипотезы посредничества используй `suspected`, а не `confirmed`.
Каждый флаг выводится независимо; оба вместе получают отдельное жирное предупреждение о высокой вероятности отказа от проекта.
`render-analysis` и `validate-analysis --render` выводят блок перед пятью этапами; для канонического `ꘖ/KB/Analysis.json` синхронизируют его также в `.md` сразу после заголовка проекта.
Ссылки в корневой карточке ведут в identity-тезисы Analysis.json, а в отчёте — к соответствующим заголовкам.
Генератор сохраняет байты карточки вне блока и предыдущие версии в `ꘖ/data/red-flags-history`.
Блок ограничен `<!-- upwork-init:red-flags:start -->` и `<!-- upwork-init:red-flags:end -->`; его ручные изменения/повреждённые маркеры дают conflict и сохраняются для явной сверки.
Ранний блок можно внести вручную по уже проверенным данным; при конфликте согласуй его с новым блоком, не заменяй всю карточку.
Явный проверенный `red_flags: []` снимает прежний управляемый блок; историю оснований сохраняй в KB.
Перед публикацией окончательного ответа воспроизведи тот же состав/статусы рисков в самом начале ответа, адаптируя ссылки к чату; прежние журнальные ответы не переписывай.

В `websites` явно укажи URL сайта клиента/целевого проекта или null, роль client/target и basis_id из identity. Корневой `.md` показывает эти адреса, оценку и доказательство; имя папки не используется как подтверждение.
История служебного Progress.md не копится; исходные доказательства, версии анализа и review packages сохраняются.

## Независимая рецензия

```text
python <инструмент> prepare-review <проект> --parent <UUID родителя> --risk routine
```

Для значимого спорного вывода/архитектуры выбирай significant; нужно два независимых A.A.
Используй штатный инструмент делегирования по адаптеру среды: в Antigravity invoke_subagent с TypeName self/Model inherit, в Codex spawn_agent с ролью A.A и моделью/effort по выбору родителя.
Передай точный корень и полный путь package из результата; пакет неизменяем и связан с текущими хешами KB, первичных Evidence и ручных входов.
В Codex аудитор сначала выполняет `review-input <проект> --package <путь> --platform codex` и выводит полный JSON инструмента; квитанция нативного выполнения связывает его с конкретным пакетом при зашифрованном назначении.
Передай goal: проверить пять этапов, первичные доказательства, альтернативы и непротиворечивость KB.
Не передавай рецензенту намеренный вывод и отчёт другого рецензента.
Его отдельный JSON-отчёт содержит package, scope всех пяти этапов + kb_consistency, result approved/needs_changes, findings.
Каждое замечание хранит claim_id, severity, status open/resolved/rejected, disposition и evidence; перед approved существенные замечания обработаны с доказательствами.
После исправления KB нужен пакет/рецензия соответствующей версии; рецензент проверяет затронутое, повторный весь сбор не обязателен.

```text
python <инструмент> native-review-proof <проект> --parent <UUID> --reviewer <UUID дочернего A.A>
python <инструмент> record-review <проект> --parent <UUID> --reviewer <UUID дочернего A.A> --report "ꘖ/KB/Evidence/Reviews/review.json"
```

В отчёте native_evidence ссылается на proof (путь относительно проекта).
Proof берётся из нативных данных выбранной среды: подтверждённая связь родителя с отдельным A.A, его назначение, выбор модели и успешное завершение. Незавершённый исполнитель или работа без назначения рецензии не считаются аудитом A.A.
Codex сверяет фактические model/effort с нативным spawn_agent родителя; Antigravity сохраняет проверку self/inherit и доступных ID моделей. Точная версия/High Antigravity могут остаться непроверенными.
Смысл рецензии и источников проверяет A.A; программная квитанция этого не доказывает.

## Журнал, внешний экспорт и метрики

```text
python <инструмент> record-answer <проект> --response-file -
python <инструмент> stage <проект> finalize --input "ꘖ/KB/Analysis.json" --output "ꙮ/1 - Анализ/res/<N>.md"
```

record-answer связывает все ещё не записанные точные запросы с одним реальным окончательным ответом, сохраняет полные пары и явную группу общего ответа.
Доставка сообщения в UI не считается подтверждённой записью файлов; публикуй в чате ровно сохранённый ответ.
Ответ после сбоя публикации восстанавливается из сохранившейся группы, без вымышленного промежуточного сообщения.
Полный Context.md собирается после текущей предметной проверки/проверки KB и журнала и передаётся внешнему агенту вручную.
Внутренним исполнителям передавай точные профильные модули KB и источники; Context.md им не нужен.

metrics принимает явно выбранные полные JSONL-трассы, не копирует reasoning и не запускает модели.
Optional --project <проект> добавляет зарегистрированные cache hits/новые попытки, поиски/смены метода и обработку findings; предыдущая незарегистрированная активность неизвестна.
Для разбивки по этапам optional --bindings содержит conversation UUID -> список stage/first_step/last_step; без доказанной привязки используется unassigned.
Не суммируй повторные экспорты одного шага; неизвестные token fields остаются неизвестными, кеш учитывается отдельно.
Токены не равны проценту квоты/валюте; качество оценивается полнотой доказательств, замечаниями рецензентов и их обработкой.
