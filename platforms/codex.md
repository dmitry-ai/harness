# Адаптер Codex

Эти указания применяются в Codex в области Upwork.
Единый конфиг сред, ролей и моделей — `AI/primary/result/.agents/runtime.json` относительно корня репозитория.
Общий навык и сценарий — `AI/primary/result/.agents/skills/upwork-init/SKILL.md`.
Общий инструмент — `AI/primary/result/.agents/scripts/upwork_project.py`.
Каждой внутренней команде передавай `--platform codex`; профиль C1/C2 определяется по `CODEX_HOME`, при неоднозначности передавай `--codex-profile` явно.
`doctor --platform codex` показывает модели по умолчанию, политику выбора и ограничения проверки; не подменяй им фактические метаданные сессии.
После изменения общих правил, ролей или runtime выполни `build-native`, затем `build-native --check` до следующего запуска/делегирования.
Нативные инструкции и TOML ролей генерируются; редактируй их канонические источники.

Новый анализ запускается навыком `/upwork-init <URL>` или `$upwork-init <URL>`.
Сценарий и пять этапов общие для обеих сред; команды выполняет агент, пользователь вводит только запросы.
Для A.A/A.F используй штатные инструменты субагентов текущего чата; роли и нужные модели прочитай в runtime/doctor.
Если инструмент поддерживает выбор именованного типа агента, используй нативную роль из runtime; при API без такого параметра передай роль и общий agents/worker.md в задании, не придумывай неподдерживаемые аргументы.
Модель и effort субагента выбирает родитель по сложности конкретной задачи, доступным моделям и политике runtime.
Модель основного /upwork-init определяется текущим чатом в UI; A.A — роль ответственности, а не имя обязательной модели.
Получай доступные идентификаторы и режимы из текущей среды, не угадывай их по памяти.
Для ясного извлечения можно выбрать более лёгкую доступную модель; для неоднозначной предметной проверки выбирай достаточную глубину.
Если оснований менять модель нет, используй резервное наследование текущей модели и effort.
В задании запиши роль, краткое основание выбора и нужный результат.
Для иной модели явно передавай её идентификатор и reasoning_effort штатному spawn_agent; в collaboration используй fork_turns: none и передай необходимые входы.
Для наследования не задавай переопределения модели/effort.
Нативный адаптер сверяет выбранные родителем параметры с фактическим turn_context дочернего агента.
В задании независимому аудитору явно укажи роль A.A, точный путь пакета `prepare-review`, источники, выходной отчёт и критерий завершения.
Дочерний аудитор сначала выполняет `review-input <проект> --package <путь пакета> --platform codex` общим инструментом и выводит полный JSON-результат команды в нативный журнал инструмента.
Эта команда проверяет версии пакета; затем аудитор читает его модули и источники и выполняет предметную проверку.
Нативное назначение может быть зашифровано: адаптер связывает исходный и дочерний ciphertext, а конкретный пакет подтверждает фактическим вызовом review-input и его результатом. Ciphertext не выдаётся за прочитанный текст.
Проверь завершение штатным инструментом ожидания; для квитанции `native-review-proof` используй действительные UUID родителя и дочернего чата.
Не создавай пользовательские чаты через `codex exec`, SDK или скрытые API для исполнения моделей.

Регистрация использует только существующий UI-помощник Shared-Projects через его именованный канал.
`init` и `register` возвращают общий ID, назначения папок и отдельные штатные ID C1/C2.
`status: pending`/`complete: false` — сохранённый запрос, а не завершённая регистрация.
Дождись регистрации исходного профиля, используя повторный идемпотентный `register`; проверь `profiles` и `folder_path`.
Если приложение ожидает штатного подтверждения папки, сообщи об этом пользователю, сохрани состояние и продолжи после его ответа.
Не пиши напрямую в catalog.json, ui-folders.json, SQLite или глобальные регистрации Codex; не подделывай `approvedBy`.
Дерево и проект общие для C1/C2, свёрнутые ветки и чаты принадлежат профилю.

Точные запросы и происхождение рецензий читает адаптер Codex из выбранного профиля только в режиме чтения.
`adopt-requests` использует UUID текущего чата (`CODEX_THREAD_ID`), `record-answer` — точный окончательный ответ.
При продолжении из другой системы сохраняй её журнал и доказательства; прежняя платформа квитанции остаётся частью происхождения.
Не реконструируй запросы из summary и не объявляй неподтверждённую квитанцию проверенной.
